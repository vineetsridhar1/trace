Prove every cloud computer stays inside its organization

A user’s own cloud computer is allowed to use the credentials that user supplied. The security goal is to make it impossible for anyone in Organization A to connect to, control, or learn details about a cloud computer belonging to Organization B.

5 stages No credential redesign Cross-organization security Approval required before coding

The rule we are protecting

Allowed

  • Alice starts a cloud session in Organization A.
  • Alice’s container uses the credentials Alice supplied.
  • Other authorized members of Organization A use the session features their role allows.
  • A deliberately public app preview may be viewed through its limited web address.

Must be impossible

  • Bob in Organization B opens Alice’s terminal.
  • Bob sends commands to Alice’s runtime by guessing or copying an ID.
  • Bob connects to Alice’s bridge or private preview.
  • Bob reads Alice’s files, Git repository, runtime details, or credentials.
The important identity is a pair: organization plus runtime. A runtime ID by itself must never be enough to find or control a cloud computer.

Why more work is useful

The main runtime router is shared by every organization. It supports organization-aware lookups, and the most sensitive paths already use them. However, some lower-level helper methods still accept only a runtime ID. They are safe only when every caller has already performed the correct organization check.

Risk: a future caller could accidentally use one of those ID-only helpers without checking the organization first. The plan removes that easy-to-make mistake and adds tests that attack every entry point from the wrong organization.

If any part does not match, Trace returns a generic “not found,” “not authorized,” or “runtime unavailable” response. It must not reveal whether the other organization’s runtime exists, who owns it, or what it is called.

Implementation stages

Map every doorway into a runtime

List every place that can connect to or send work to a cloud computer: bridge connection, terminal, file actions, Git, HTTP previews, preview WebSockets, app processes, restart/reconnect, and background export jobs. Record where the user, organization, session, and runtime are checked today.

Require organization plus runtime everywhere

Change the shared runtime router so cloud and local runtimes are both stored and found using the organization and runtime ID together. Change command helpers so the organization is required rather than optional. Session-based commands must also include the saved “home runtime” so they cannot fall through to another connection.

Harden every doorway

Make terminal, preview, Git, bridge, file, and background-job paths follow one rule: load the object inside the caller’s organization first, check the caller’s permission, then send only to that object’s saved runtime. Public previews remain intentionally viewable, but they expose only the app’s web traffic—not terminal or general runtime controls.

Add cross-organization attack tests

Create Organization A and Organization B with deliberately similar data, including the same fake runtime ID where possible. Try every Organization A token, user, session ID, endpoint key, terminal ID, and Git token against Organization B. Every attempt must fail without leaking identifying details or delivering a command.

Verify the AWS wall and add monitoring

Turn the observed AWS settings into repeatable deployment checks: no inbound runtime security-group rules, ECS Exec disabled, no task-role permissions, and no route that lets one runtime contact another directly. Add safe security telemetry for rejected organization/runtime mismatches without logging credentials or sensitive IDs unnecessarily.

Attack tests we will run

What this plan does not change

Still true

  • A user’s own cloud container receives and uses that user’s supplied credentials.
  • Cloud containers remain temporary.
  • Local sessions keep the same credential model.
  • Authorized Trace AWS operators retain their infrastructure access.

Not being built

  • No credential middleman or AI request proxy.
  • No Secrets Manager migration solely to hide keys from their own container.
  • No change to normal Claude, Codex, or Git behavior.
  • No broad rewrite of organization permissions outside runtime-facing paths.

Technical appendix

The central change is in apps/server/src/lib/session-router.ts. The audit and protections cover bridge-handler.ts, terminal-handler.ts, services/terminal.ts, services/runtime-access.ts, services/endpoint-proxy.ts, services/managed-git.ts, and the session/application callers that send commands through the router.

Tests will extend the matching *.test.ts files rather than creating a separate security framework. AWS network and role settings must be checked in the infrastructure stack that owns trace-prod-session-runtime; that stack is not present in this repository and must be located before infrastructure changes are made.
