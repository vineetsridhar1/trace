Cloud browser video artifacts

Give cloud-session agents a built-in skill and deterministic runner for exercising a localhost app in headless Chromium, turning the browser run into a compact WebM recording, and publishing it through Trace’s existing video-artifact flow.

9 implementation files4 phasesCloud runtime onlyNo schema migration

Scope

In scope

  • A browser-video runtime skill agents can discover and follow.
  • A small, recipe-driven runner that launches system Chromium, drives a tab, captures frames, and encodes WebM.
  • Bundled cloud-image dependencies and a runtime command that keeps the agent workflow stable.
  • Upload through $TRACE_CLI artifact push video, yielding the existing session event and playable artifact card.

Explicitly not doing

  • No GraphQL, Prisma, storage, or web-client feature work: video artifacts already exist.
  • No recording of a user’s local Chrome, audio capture, arbitrary remote sites, or persistent browser profiles.
  • No availability in desktop/local sessions in this first slice; the runner relies on the provisioned image.
  • No generalized browser-control product surface or new agent tool protocol.

Current state and chosen seam

apps/container-bridge/src/bridge.ts gives each cloud invocation the bundled runtime paths, TRACE_CLI, and TRACE_SKILLS_DIR. runtime/manifest.json is the source list embedded into packages/shared/src/trace-runtime.generated.ts; therefore a runtime skill is available without changing the session service or resolver.

apps/server/src/services/artifact.ts already normalizes video to trace.video.v1, validates that the archive contains video media, stores it, and emits artifact_created. apps/web/src/components/artifact/MediaArtifact.tsx and MediaArtifactUploadedCard.tsx already play and present that event. The implementation follows the existing runtime artifact skill rather than creating a competing upload API.

apps/container-bridge/Dockerfile already supplies system Chromium. The design-starter review script is the sibling pattern for launching playwright-core against system Chromium; the new runner will reuse that execution model but record a scripted app run instead of only taking screenshots.

The runner accepts a local URL, viewport, a finite sequence of safe browser actions (navigate, wait, click, type, key press, and pause), and recording options. It launches a fresh headless Chromium process with sandbox-safe cloud flags, drives only that page, samples screenshots at a bounded frame rate, encodes a WebM with ffmpeg, and exits with clear failure output. The skill requires the agent to start and smoke-test its preview first, keep recordings brief, inspect the generated video metadata, then upload only the finished media file.

Why WebM: it is already accepted by the artifact bundle, directly playable in the existing web UI, and avoids assuming a proprietary H.264 encoder in the Debian runner image.

Implementation phases

Package the recording capability in the cloud image

Add the minimal automation and encoding dependencies to the provisioned runtime image. Add a focused runner module plus executable wrapper with explicit environment/configuration boundaries; it must never require a browser download or network package install during a session.

Make it agent-usable through the runtime

Add the browser-video skill with a concise contract, action-recipe example, duration/size limits, localhost-only guidance, cleanup rules, and the final artifact push video command. Add its files to the runtime manifest and regenerate the embedded runtime bundle so new cloud invocations receive it.

Harden runner behavior

Validate recipe shape and URL policy before launch; enforce fixed maximum duration, action count, frame rate, viewport, and output path handling; always close browser/ffmpeg processes and remove temporary frames on success or failure. Report actionable errors for an unavailable preview, failed selector/action, Chromium failure, encoder failure, or missing output.

Verify the full artifact handoff

Unit-test validation, command construction, action dispatch, and cleanup with injected process/browser seams. Build the cloud image, run a small local app through the runner, confirm WebM structure and size, publish it with the existing CLI, and verify the resulting artifact_created event displays as a playable video card.

Risks and mitigations

Video recording is resource-intensive. Headless browser capture plus encoding can consume CPU and disk in a shared cloud runtime. Limit recording duration, frame rate, dimensions, action count, and output size; clean all temp data; fail before uploading an oversized capture.
Untrusted navigation must not become an egress feature. The first version accepts localhost/loopback preview URLs only. Recipes cannot supply arbitrary Chromium flags, shell snippets, downloads, or persistent profile locations.
Automation can be flaky. Use explicit waits and selector/action failures in the recipe, require the agent to test the app before recording, and surface a readable error instead of publishing a partial capture.
