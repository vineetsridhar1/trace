CLI-driven durable application publishing

Let the app-building AI inspect its project and invoke one safe Trace CLI workflow. Trace validates the committed deploy manifest, builds either a static bundle or a private service, adds PostgreSQL only when requested, and promotes one stable URL. The development session can then hibernate without stopping or erasing the published result.

Approval decision

Recommended v1: expose one agent-facing app CLI workflow with two internal deployment modes. The AI may explain and request static or service, but a committed manifest plus Trace service validation is authoritative. Static output is stored in private S3; services run on ECS and receive an isolated Aurora database only when the manifest declares PostgreSQL.

AI proposes, CLI and service verify · recommended

The agent inspects user intent and project evidence, writes .trace/app-starter.json, commits it, then invokes "$TRACE_CLI" app publish --mode auto --json. The CLI reports the resolved mode and blockers; the service revalidates the immutable checkpoint before creating desired state.

One Publish concept for users; no AWS vocabulary or hosting-plan questionnaire.

AI directly selects AWS resources · rejected

Letting a prompt choose S3, ECS, secrets, or Aurora without a checked contract makes retries, security, UI state, and future migrations unpredictable.

The AI chooses product capabilities; Trace owns infrastructure translation.
Database sub-decision: direct Aurora TLS remains the recommended service-mode v1

When capabilities.postgres is true, create one database, login, and secret per app on the shared app-data Aurora cluster. Inject only that app secret, cap its pool at two, and defer the current RDS Proxy because it registers only the cluster admin secret.

Scope

In scope

  • Publish only an immutable Git checkpoint.
  • Add discoverable app inspect, app publish, and app status CLI commands.
  • Resolve a committed deploy manifest to static or service with evidence.
  • Build static output into a digest-addressed private S3 bundle.
  • Build service output into a digest-addressed ECR image.
  • Provision PostgreSQL and run migrations only when declared.
  • Create/update one private ECS Fargate service only for service mode.
  • Promote a stable *.apps.<domain> route after health passes.
  • Preserve data across task restarts, republishes, and dev-session hibernation.
  • Expose lifecycle status through Trace events and the application card.

Not doing

  • No Redis service or REDIS_URL for generated apps.
  • No durable local-development database promise.
  • No multi-region failover or per-app autoscaling in v1.
  • No persistent file/object storage in this slice.
  • No destructive migration rollback; schema changes follow expand/migrate/contract.
  • No silent database deletion on unpublish.
  • No free-form AWS resource creation from the agent runtime.
  • No trusting an uncommitted local build as the production artifact.

Proposed commands

  • app inspect [path] --json: read local files, validate the manifest, and return detected facts, recommended mode, required capabilities, and blocking contradictions. No Trace state changes.
  • app publish --mode auto|static|service --json: request publication of the current app's latest immutable checkpoint with an idempotency key. auto is the normal path.
  • app status [--follow] --json: return the desired mode, resolved mode, phases, URL, and safe failure details from deployment events.
  • Later lifecycle leaves: app unpublish, app rollback, and explicit destructive deletion.

Authorization and ownership

  • Add narrow app:read and app:deploy invocation capabilities.
  • Register exact GraphQL documents and permitted argument paths in packages/cli-contract.
  • Server authorization restricts every command to TRACE_SESSION_GROUP_ID; the AI never supplies another app's binding or credentials.
  • The CLI calls the same service layer as the web Publish button. Only the service creates deployment records and events.
  • Help must describe effects clearly: inspect is read-only; publish creates shared external state and runs only after the user requests publishing.
Conclusion: the CLI is a typed agent control surface, not the AWS deployment engine

The runtime may perform a local preflight build to give fast feedback, but production is rebuilt from the committed checkpoint by the AWS workflow. The CLI must not upload arbitrary uncommitted HTML straight to the public bucket, create ECS services itself, receive admin database credentials, or bypass Trace's desired-state and event model.

End-to-end publish flow

Static branch

For literal HTML or a browser-only build: run the declared build, verify the output directory and fallback behavior, store the immutable bundle under a deployment/content digest in private S3, then promote the route.

No per-app task, database, migration, secret, or always-on compute.

Service branch

For API routes, server-only secrets, integrations, authentication callbacks, WebSockets, or persistence: build an image, optionally provision PostgreSQL and migrate, reconcile ECS, verify health, then promote.

Integrations force service mode because provider calls stay in server routes.
  1. The AI runs app inspect, resolves contradictions with the project or user, commits the manifest and source, and invokes app publish --mode auto.
  2. Trace re-reads the latest checkpoint, validates the manifest and authorization, locks the app, records requested and resolved capabilities, uploads source, and enqueues a versioned job.
  3. A Standard Step Functions execution named by deployment ID owns retries and ordering. Static runs build → verify bundle → store S3 → promote. Service runs build image → optional data/migration → reconcile ECS → health → promote.
  4. Each phase calls Trace’s internal callback. The service layer validates the transition, records it, and emits the event consumed by the UI.
  5. The previous live route remains active until the replacement passes all gates. Any failure marks the attempt failed without taking the prior revision down.
Classification rules: the AI owns semantic intent; deterministic evidence prevents unsafe choices
  • The AI sets the manifest from the user's requested behavior. app inspect reports mechanical facts and contradictions; it does not pretend arbitrary source-code inference is perfect.
  • Static is valid only when the declared build produces files and no request-time server capability is required. The untouched starter's dormant server.ts and installed pg package are not enough to force service mode.
  • Declared API routes, private environment variables, live integration bindings, authentication callbacks, WebSockets, background work, or PostgreSQL require service mode.
  • The agent may deliberately request service mode for future functionality, but cannot force static when validation finds a server requirement.
  • Mode changes preserve the app ID and URL. Moving static → service may create a retained database; moving back to static never silently deletes it.

PostgreSQL lifecycle

Identity and isolation

  • Stable app UUID maps to a generated database name and login role; slugs never become SQL identifiers.
  • A VPC-only provisioner uses the Aurora admin secret. The app never receives it.
  • The app receives only its own DATABASE_URL through ECS secret injection.
  • The execution role may read the generated-app secret prefix; the container task role receives no Secrets Manager or control-plane data permission.
  • Connections require TLS and the starter caps its pool at two connections.

Creation, reuse, deletion

  • First publish: create database, login, grants, and secret idempotently.
  • Republish/rollback: reuse the same data binding and run the target image's migration command.
  • Task replacement or dev hibernation: no database change.
  • Unpublish: remove route and stop ECS; retain database by default.
  • Permanent app deletion: explicit destructive flow revokes role, schedules final backup/retention, then drops data.
Conclusion: the app’s data survives every runtime lifecycle event except explicit permanent deletion

The authoritative app-to-database mapping lives in Trace as an AppDataBinding. It records the shard, generated identifiers, secret ARN, and lifecycle state—but never the password. Provisioning uses PostgreSQL advisory locking plus existence/ownership checks so queue retries cannot create divergent identities.

State and failure semantics

queued→ validating→ building→ preparing_target→ deploying→ verifying→ live
Every non-terminal phase may fail. Trace records a safe error summary and external execution ID. Source secrets and database URLs are scrubbed. A failed attempt never promotes its route, and the last live revision remains served.
Conclusion: supersede pending attempts, never supersede the last live deployment until promotion succeeds
  • A new publish supersedes older queued/in-progress desired state, but running AWS executions receive a cancellation signal and still finish cleanup.
  • Republishing the same deployment ID or checkpoint is idempotent across the CLI retry, GraphQL mutation, SQS delivery, Step Functions start, bundle/image creation, optional database provisioning, and route promotion.
  • Migration failure leaves the current ECS service and route unchanged. Rollback deploys a previous image as a new attempt and reuses the database; it does not automatically reverse schema.
  • Each deployment records requestedMode, resolvedMode, manifest digest, target digest, and capabilities so UI and operations can explain why a branch was selected.

Risks and mitigations

Aurora connection exhaustion. Direct connections are simple but finite. Enforce a pool cap of two per task, desired count one, connection timeouts, Aurora alarms, and a canary concurrency gate; revisit proxying before autoscaling.
AI misclassifies a project. Treat AI reasoning as a proposal, require a versioned manifest, return evidence from CLI inspect, and revalidate the committed checkpoint on the server. Server-required features always force service mode.
Static bundles execute hostile browser content. Store privately, serve through the user-content/app boundary with strict headers, reject unsafe paths and symlinks, cap files and bytes, and never grant the bundle AWS credentials.
CLI becomes a second business-logic layer. Keep local inspect deterministic and shared; publication calls the same service method as the UI. The service alone authorizes, creates desired state and events, and translates capabilities into infrastructure.
Cross-app credential exposure. Never pass the admin secret through jobs. ECS injects only the referenced app secret, the container task role has no Secrets Manager permission, SQL identities are UUID-derived, and isolation gets a negative integration test.
Migration damages shared live data. Run migrations before traffic, require idempotent expand/migrate/contract changes, keep timeouts and logs, and never attempt automatic down migrations on rollback.
Orchestrator retries create duplicate AWS resources. Use deployment ID as the Step Functions execution key and stable names for database, service, task family, and route; every reconciler performs describe-before-create/update.
Gateway becomes a new availability boundary. Start with one task only for the gated v1 rollout, add health/alarms and restart recovery, keep the route mapping durable in Trace, and require a tested HA design before wider production scale.

Approval means

Proceed with this sequence and boundary: one managed app CLI workflow; AI-proposed but deterministically verified capabilities; static bundles on private S3; services on private ECS; PostgreSQL only when declared, with a database-per-app on shared Aurora and direct TLS for v1; no generated-app Redis; and one stable route promoted only after target-specific verification. Implementation stops at each phase gate if its proof fails.
