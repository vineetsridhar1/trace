Durable published applications

Turn Publish into an independent AWS deployment: an immutable commit becomes an image, gets isolated PostgreSQL data, passes migrations and health checks, and is promoted to a stable app URL. Development sessions can then hibernate without stopping the published app.

Approval decision

Recommended v1: use a database and login per app on the shared app-data Aurora cluster, with direct TLS connections and a tiny application pool. Keep the current RDS Proxy out of generated-app traffic until its authentication model is redesigned.

Direct Aurora TLS · recommended

One secret per app, injected only into that app's ECS task definition. Simple tenant isolation and no dynamic proxy-auth registration.

Tradeoff: cap each app pool (initially 2) and monitor aggregate connections.

RDS Proxy per-app credentials

The current proxy registers only the cluster admin secret. Registering every app secret expands operational and quota pressure.

Defer until IAM end-to-end auth or another scalable proxy identity design is approved.

Scope

In scope

  • Publish only an immutable Git checkpoint.
  • Build and store a digest-addressed image in ECR.
  • Provision one PostgreSQL database, role, and secret per app.
  • Run an idempotent migration task before serving traffic.
  • Create/update one private ECS Fargate service per app.
  • Promote a stable *.apps.<domain> route after health passes.
  • Preserve data across task restarts, republishes, and dev-session hibernation.
  • Expose lifecycle status through Trace events and the application card.

Not doing

  • No Redis service or REDIS_URL for generated apps.
  • No durable local-development database promise.
  • No multi-region failover or per-app autoscaling in v1.
  • No persistent file/object storage in this slice.
  • No destructive migration rollback; schema changes follow expand/migrate/contract.
  • No silent database deletion on unpublish.

  • apps/server/src/services/app-deployment-dispatcher.ts streams a size-limited Git archive to S3 and enqueues a versioned SQS job.
  • apps/server/src/routes/app-deployment-callback.ts authenticates internal deployment status updates.
  • AppDeploymentCard.tsx displays queued/building/deploying/live/failed state and the live URL.

Build and data primitives are present

  • infra/lib/app-deployment-stack.ts owns the queue, worker, CodeBuild project, ECR repository, ECS cluster, and shared task roles.
  • infra/lambda/app-deployment-worker/index.ts validates provenance and starts CodeBuild idempotently.
  • infra/lib/data-stack.ts can create a separate Aurora PostgreSQL app-data cluster and proxy when enableAppData is enabled.
  • Wildcard app DNS reaches the ALB, but the listener deliberately returns the placeholder “App gateway is not deployed.”

The current workflow stops at “deploying”

No component provisions an app database, runs migrations, creates an ECS service, verifies health, or promotes the wildcard route. The Aurora feature is intentionally disabled in production examples.

The smoke script is also stale: scripts/smoke-cloud-app-session.mjs still expects the old public-preview mutation and a development Redis process.

Repository prerequisite: both open feature branches are behind their respective default branches. Implementation starts by rebasing the Trace and trace-ops work, resolving contracts together, and rerunning both suites before adding behavior.

End-to-end publish flow

  1. Trace locks the app, chooses the latest checkpoint, creates a deployment record, uploads the source archive, and enqueues a versioned job.
  2. A Standard Step Functions execution named by deployment ID owns retries and ordering: build → provision/reuse data → migrate → reconcile ECS → verify → promote.
  3. Each phase calls Trace’s internal callback. The service layer validates the transition, records it, and emits the event consumed by the UI.
  4. The previous live route remains active until the replacement passes all gates. Any failure marks the attempt failed without taking the prior revision down.

PostgreSQL lifecycle

Identity and isolation

  • Stable app UUID maps to a generated database name and login role; slugs never become SQL identifiers.
  • A VPC-only provisioner uses the Aurora admin secret. The app never receives it.
  • The app receives only its own DATABASE_URL through ECS secret injection.
  • The execution role may read the generated-app secret prefix; the container task role receives no Secrets Manager or control-plane data permission.
  • Connections require TLS and the starter caps its pool at two connections.

Creation, reuse, deletion

  • First publish: create database, login, grants, and secret idempotently.
  • Republish/rollback: reuse the same data binding and run the target image's migration command.
  • Task replacement or dev hibernation: no database change.
  • Unpublish: remove route and stop ECS; retain database by default.
  • Permanent app deletion: explicit destructive flow revokes role, schedules final backup/retention, then drops data.
Conclusion: the app’s data survives every runtime lifecycle event except explicit permanent deletion

The authoritative app-to-database mapping lives in Trace as an AppDataBinding. It records the shard, generated identifiers, secret ARN, and lifecycle state—but never the password. Provisioning uses PostgreSQL advisory locking plus existence/ownership checks so queue retries cannot create divergent identities.

State and failure semantics

queued→ building→ provisioning_data→ migrating→ deploying→ verifying→ live
Every non-terminal phase may fail. Trace records a safe error summary and external execution ID. Source secrets and database URLs are scrubbed. A failed attempt never promotes its route, and the last live revision remains served.
Conclusion: supersede pending attempts, never supersede the last live deployment until promotion succeeds
  • A new publish supersedes older queued/in-progress desired state, but running AWS executions receive a cancellation signal and still finish cleanup.
  • Republishing the same deployment ID or checkpoint is idempotent across SQS delivery, Step Functions start, database provisioning, task-definition registration, and route promotion.
  • Migration failure leaves the current ECS service and route unchanged. Rollback deploys a previous image as a new attempt and reuses the database; it does not automatically reverse schema.

Risks and mitigations

Aurora connection exhaustion. Direct connections are simple but finite. Enforce a pool cap of two per task, desired count one, connection timeouts, Aurora alarms, and a canary concurrency gate; revisit proxying before autoscaling.
Cross-app credential exposure. Never pass the admin secret through jobs. ECS injects only the referenced app secret, the container task role has no Secrets Manager permission, SQL identities are UUID-derived, and isolation gets a negative integration test.
Migration damages shared live data. Run migrations before traffic, require idempotent expand/migrate/contract changes, keep timeouts and logs, and never attempt automatic down migrations on rollback.
Orchestrator retries create duplicate AWS resources. Use deployment ID as the Step Functions execution key and stable names for database, service, task family, and route; every reconciler performs describe-before-create/update.
Gateway becomes a new availability boundary. Start with one task only for the gated v1 rollout, add health/alarms and restart recovery, keep the route mapping durable in Trace, and require a tested HA design before wider production scale.

Approval means

Proceed with this sequence and boundary: two coordinated repositories, durable AWS orchestration, database-per-app on shared Aurora, direct TLS for v1, no generated-app Redis, and route promotion only after migration and health. Implementation will stop at each phase gate if the stated verification does not pass.
