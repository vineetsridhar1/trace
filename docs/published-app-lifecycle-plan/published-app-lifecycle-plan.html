The idea in one minute

Think of the cloud session as a workshop. It is where the AI edits files, runs previews, and tests ideas. Workshops can close when nobody is using them. Publishing creates a separate storefront that stays open even after the workshop closes.

Temporary workshop

  • The AI works here.
  • The live editing preview runs here.
  • It may shut down after inactivity.
  • Running processes stop when it shuts down.

Permanent storefront

  • Created only when Publish is requested.
  • Has a stable public web address.
  • Runs separately from the workshop.
  • Keeps its saved data until explicitly deleted.

What the user experiences

  1. The user asks the AI to make a page or app.
  2. The user asks to publish it.
  3. The AI checks what the project actually needs.
  4. Trace chooses the simplest safe hosting path.
  5. Trace shows progress such as “checking,” “building,” and “live.”
  6. The user receives one permanent link.

The user never chooses “S3,” “ECS,” a container size, or a database plan. Those are internal tools. The product remains one button and one understandable result.

The two automatic paths

Path A · store finished files

A simple page is already complete when its HTML, styles, JavaScript, and images are built. Trace stores those finished files and sends them to visitors when they open the link.

  • Good for landing pages, portfolios, mockups, calculators, and interactive pages whose code runs entirely in the visitor's browser.
  • No private server runs all day.
  • No database is created.
  • Faster and cheaper than running a full application server.

Path B · keep an application running

A full app needs code to run whenever a visitor makes a request. Trace keeps that code running separately from the development session and adds a database only if the app needs to remember information.

  • Needed for private API keys, sign-in callbacks, server routes, live connections, or background work.
  • Needed for Trace integrations because provider credentials must remain on the server.
  • A database is optional, not automatic.
  • More capable, but costs more than finished-file hosting.
The AI understands intent; Trace checks safety. The AI records what the app needs in a small project file. Trace checks that declaration against facts it can verify. A simple-looking page cannot use the cheap path if it secretly needs a private server.

1. The AI inspects the project

The AI uses the Trace CLI—a private command-line tool available inside Trace—to ask, “Can this be a simple page, or does it need a running server?”

Implementation detail: proposed CLI commands

JSON is structured text that an AI or program can read reliably.

  • "$TRACE_CLI" app inspect --json reports facts, a recommended path, warnings, and blockers without changing anything.
  • "$TRACE_CLI" app publish --mode auto --json requests publication of the current app only.
  • "$TRACE_CLI" app status --json reports progress and safe errors.

2. Trace saves an exact version

Trace publishes a Git checkpoint: a permanent snapshot of the project at one exact moment. Unfinished edits made later cannot secretly change that deployment.

Why Trace does not publish loose files from the temporary session

The temporary session can disappear during publishing. Building again from the saved checkpoint makes the result repeatable, reviewable, and safe to roll back.

3. AWS builds the permanent version

AWS means Amazon Web Services, the cloud provider already used by Trace. Its background workflow rebuilds the saved checkpoint so production does not depend on the temporary workshop.

Implementation detail: the background checklist

Trace uploads the source to S3, places a job in SQS, and uses Step Functions to remember which steps have finished. CodeBuild creates either a static file bundle or a container image. These services are explained in the glossary below.

4. Trace proves the new version works

Static files are checked for a valid home page, safe paths, correct file types, and size limits. A full app must start successfully, pass its health check, and complete any database update.

5. Trace moves the public link

The old version stays public during all earlier steps. Only after the new version passes every check does Trace point the stable web address at it.

What happens on each path

The same app can change paths later. A landing page can grow into a full app without changing its public address. Returning to a simple page does not silently delete a database created earlier.

Plain-language infrastructure glossary

S3 · a secure file cabinet

Amazon S3 stores files durably. For a simple page, Trace stores the finished HTML, CSS, JavaScript, and images here. The storage stays private; visitors receive files through Trace's public gateway.

ECS and Fargate · an app keeper

ECS tells AWS which application should keep running. Fargate supplies the computer power. If the app process crashes, ECS starts a replacement.

Container image · a sealed app package

A container image packages the full app and its dependencies. ECR is the private library where Trace stores these packages.

Aurora PostgreSQL · durable memory

PostgreSQL is a database. Aurora is AWS's managed version. It stores information such as accounts, notes, or counters separately from the running app.

Gateway · the receptionist

The gateway receives a public web address, finds its approved deployment, and sends the visitor either stored files or the running app.

API route · a private service window

An API route lets the page ask its server to do work, such as reading saved data or using a secret key. Because that work happens when visitors make requests, it needs the full-app path.

Health check · “are you ready?”

A small automated request proves a running app started and can answer traffic before real visitors are sent to it.

Migration · update the filing system

When an app changes how database information is organized, a migration updates that structure before the new app receives traffic.

TLS · encrypted connection

TLS encrypts traffic between the running app and its database. Each app receives only its own database login, never the master password.

More background services engineers will use
  • SQS is a durable waiting line for deployment jobs.
  • Step Functions remembers the ordered deployment checklist and retries safe failures.
  • CodeBuild rebuilds production output from the saved source.
  • Secrets Manager stores passwords without placing them in source code.
  • CloudWatch collects logs, measurements, and alarms.
  • CDK is the code engineers use to describe and test the AWS resources Trace should create.

Implementation detail: one isolated database identity per app

When PostgreSQL is requested, a private provisioner creates one database, one login, and one secret for that app. Trace stores an AppDataBinding: a record connecting the app to its database without storing the password. Direct encrypted Aurora connections are recommended for the first version, with at most two reusable connections per running app. RDS Proxy—an AWS database-connection middle layer—is deferred because the current one only registers the cluster administrator secret.

What if publishing fails?

checking→ building→ preparing→ testing→ live

First publication fails

No broken public app is created. Trace shows a useful error and keeps the saved source so the AI can fix it.

An update fails

The existing public version remains online. Trace never moves the public address to an unverified replacement.

Implementation detail: safe retries and duplicate jobs

Every step uses stable deployment identifiers and “check before create” behavior. This is called idempotency: repeating a CLI request, queue message, database request, build, or route update reaches the same result instead of creating duplicates.

What about designs?

Designs use the lightweight path. A design is saved into Trace-managed Git, packaged as a viewable artifact, and served from durable file storage. It does not need a continuously running application server or database.

Implementation plan

Phase 1 · Teach Trace how to describe an app

Expand the small .trace/app-starter.json file so the AI can declare “simple page” or “running app,” its build command, and whether it needs PostgreSQL.

Engineer checklist and proof

Add the shared classifier and examples for literal HTML, a Vite page (Vite is the starter's frontend build tool), API routes, integrations, private secrets, WebSockets (long-lived live connections), and PostgreSQL. Invalid or contradictory declarations must explain exactly what blocked publication.

Phase 2 · Add safe app commands to the Trace CLI

Add inspect, publish, and status commands so the AI can use the same Trace service as the web Publish button.

Engineer checklist and proof

Change packages/cli/src/commands/app/*, packages/cli-contract/src/index.ts, and server agent authorization. Add narrow app:read and app:deploy permissions. Exact-operation, current-app, help, JSON output, permission, and repeat-safety tests must pass.

Phase 3 · Build both permanent homes

Add the private file path for simple pages and the running-service path for full apps. Add an isolated database only when requested.

Engineer checklist and proof

In Trace, extend deployment state, events, GraphQL (Trace's API schema), the second version of the deployment job message, and AppDataBinding. In trace-ops, rebase the existing worker branch, then add the static builder, workflow branches, database creator, migration task, ECS service manager, narrowly limited permissions, logs, and alarms.

Phase 4 · Give both paths one stable address

Build the shared gateway and switch an app's address only after its new target passes verification.

Engineer checklist and proof

The gateway maps the unique name in the app's web address to either a private S3 bundle or an authenticated ECS runtime. Test that one app cannot claim another app's address, the old version serves during deployment, and static → service → static keeps the same URL and retained data.

Phase 5 · Finish the product and prove it in AWS

Show understandable progress and errors, add rollback/unpublish/delete controls, then test real applications before enabling production broadly.

Engineer checklist and proof

Update the event-driven Zustand browser state store and rewrite scripts/smoke-cloud-app-session.mjs. Test a literal HTML page, Vite page, server app, and PostgreSQL app with a small internal group first. Put development to sleep, replace a running ECS process, republish, roll back, change between hosting paths, and intentionally fail a build and migration.

What already exists and what is missing

Already built

  • Trace can choose a saved checkpoint and create a deployment record.
  • Trace can upload source and queue a deployment job.
  • The UI can show basic deployment status.
  • The managed CLI already has secure commands, machine-readable help, exact permission checks, and safe retry patterns.
  • trace-ops already has the build queue, image builder, image library, ECS cluster, and optional Aurora foundation.

Still needed

  • The new app CLI commands and project classifier.
  • The permanent static-file path.
  • The database creator and migration runner.
  • The service creator and health verifier.
  • The shared gateway and safe route switch.
  • Complete lifecycle controls, monitoring, and real AWS tests.
Source-backed repository notes
  • apps/server/src/services/app-deployment.ts owns current publish requests and guarded callbacks.
  • packages/cli and packages/cli-contract provide the pattern for agent-facing commands.
  • apps/server/src/services/session.ts currently tells App sessions to build full-stack apps and always advertises local PostgreSQL plus Redis, a temporary cache service; that guidance must become capability-based.
  • infra/lib/app-deployment-stack.ts on trace-ops main creates a queue, CodeBuild, ECR, ECS, and security roles, but does not attach a worker to consume the queue.
  • The unmerged trace-moose-4-app-deployments branch contains that worker and must be updated with current trace-ops main before reuse.

Main risks, in ordinary language

Trace chooses the wrong path. The AI states the intended behavior, the CLI explains what it found, and the server checks the saved version again. Any verified server-only need forces the full-app path.
One app sees another app's data. Every database app receives its own login and database. Automated tests prove app A cannot connect to app B.
An update breaks the live app. The old version keeps serving until the new build, database update, startup, and health checks all succeed.
A retry creates duplicates. Stable IDs and check-before-create behavior make repeated requests return to the same deployment.
A simple page contains unsafe files. Trace rejects unsafe paths, links, oversized bundles, and unexpected output; the storage remains private behind the gateway.

Approval means

Approve this product boundary: users get one Publish experience; the AI describes what the project needs; Trace verifies it; simple pages become durable stored files; full apps become private running services; PostgreSQL is added only when needed; designs use the lightweight artifact path; and no public address moves until the replacement is proven safe.

Implementation will proceed in the five phases above and stop at any phase whose proof does not pass.
