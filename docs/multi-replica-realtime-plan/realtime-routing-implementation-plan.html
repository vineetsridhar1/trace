Multi-replica realtime routing

Keep WebSockets inside Trace’s API replicas and add a Redis-backed runtime directory plus directed replica inboxes. Any healthy replica can then reach the replica holding a bridge, terminal, or preview connection while Postgres remains the durable business-state boundary.

Decision

Approve combined API/WebSocket replicas with a Redis backplane. Do not extract a separate WebSocket service in this change. Introduce a RuntimeTransport boundary so a dedicated gateway remains possible later without rewriting business services.

In scope

  • Runtime presence, fenced ownership, command acknowledgements, and replies.
  • Distributed terminal metadata, attachments, output, and scrollback.
  • Cross-replica preview HTTP and WebSocket proxy traffic.
  • Readiness, graceful drain, singleton jobs, rollout, and rollback.

Non-goals

  • No TCP/WebSocket migration; clients reconnect with existing behavior.
  • No exactly-once socket delivery or automatic replay of non-idempotent commands.
  • No new GraphQL mutations, event types, or client state model.
  • No replacement of Postgres events as durable truth.

Required contracts

ConcernPlanned behavior
Tenant isolationEvery key/envelope carries organization, runtime key, owner replica, and generation. Ambiguity fails closed.
PresenceAuthenticated runtime_hello registers a TTL descriptor. Heartbeats renew through compare-generation Lua; stale renewal closes the old socket.
DeliveryRemote dispatch resolves after the owner acknowledges its socket write. Ack timeout returns existing unavailable/delivery-failed behavior.
OrderingOne per-runtime queue serializes local and remote writes on the socket owner.
RepliesTransient file/branch/checkout/proxy replies route to the request origin. DB-backed setup/process/export results execute on the bridge owner.
Large payloadsInternal frames target 256 KiB; receivers cap total bytes, chunk count, and assembly lifetime using current 25 MiB endpoint and 64 MiB bridge limits.
Local modeTRACE_LOCAL_MODE uses an in-memory implementation and does not require Redis.
Redis failureLocal socket delivery continues where possible; remote delivery fails quickly and never guesses another runtime.

Implementation slices

Lifecycle foundation and compatibility flag

Fix startup/readiness and prove graceful shutdown before distributing any socket state.

Readiness, signals, drain order, and verification
  • Keep /health as the readiness-compatible path: 503 before startup and after drain begins; optionally add /health/live.
  • Install one idempotent SIGTERM/SIGINT handler that marks unready, rejects upgrades, stops mutating loops, closes sockets with 1012, stops backplane/Redis, then closes HTTP with a bounded force timeout.
  • Add TRACE_REALTIME_BACKPLANE_ENABLED; deploy code disabled before changing replica count.
  • Tests: pre-ready, ready, draining, duplicate signals, upgrade rejection, and 1012 reconnect.

Backplane, runtime directory, and async dispatch

Add replica identity, versioned inboxes, generation-fenced presence, local/remote delivery parity, and correlated replies.

Migrate the full runtime API blast radius
  • Add realtime-backplane.ts and runtime-directory.ts; initialize the inbox before readiness.
  • Broadcast presence updates so waitForBridge resolves when a bridge connects elsewhere.
  • Convert send, sendToRuntime, availability, listing, and request methods to async descriptor-backed operations.
  • Audit all production callers in session, application, managed-git, terminal, runtime-access, connections, bridge-access, endpoint proxy, and Slack routes. Services pass explicit org and persisted home runtime; local binding is not distributed truth.
  • Preserve protocol-version gates and source-runtime validation for every pending response.

Distributed terminal directory and relay

Move serializable terminal state and indexes to Redis while actual browser WebSockets remain local.

Interactive, restored, and headless terminal cases
  • Store terminal kind, org, session/channel, runtime, owner user, state, frontend owner generation, expiry, and capped 50 KiB scrollback.
  • Maintain session, session-group, and channel/runtime indexes atomically with cleanup.
  • Attach on any replica: load descriptor, perform existing owner/capability checks, claim frontend lease, replay scrollback, route output to its local socket.
  • Rehydrate activeTerminals only from organization-scoped DB records. Preserve restored-terminal, revoked-capability, and cross-org denial tests.
  • Headless executeCommand gets a short-lived callback owner; owner death causes timeout/cleanup, never duplicate execution.

Preview proxy and singleton ownership

Route preview responses to the HTTP/WebSocket owner and prevent two replicas from duplicating side effects.

Proxy framing and job leadership
  • Keep pendingHttp/pendingWs local; use origin-routable request IDs and bounded chunk reassembly.
  • Drop late responses when the origin replica is gone—its client connection is already gone.
  • Add a renewable leader lease for slackEventBridge.rehydrate(); detach local iterators immediately on lease loss.
  • Wrap design preview, PDF, animation/design-system preview, and design-system artifact reconciler iterations in named distributed locks, following existing cleanup/deprovision jobs.
  • Start singleton subscribers/intervals only after Redis/backplane readiness and stop them first during drain.

Staged two-replica rollout

Enable compatibility on one task first, then raise desired count and run placement/failure tests.

Rollout and rollback runbook
  1. Deploy code with the flag off; verify lifecycle behavior.
  2. Enable the flag with desired count one; validate presence, inbox subscription, local fast path, and telemetry.
  3. Scale to two with minimum healthy 100%, temporary surge capacity, readiness health checks, deregistration delay, and failure-domain spread.
  4. Force API A / bridge B / terminal frontend A-and-B placements; kill each owner independently.
  5. Perform a rolling deploy with active GraphQL subscriptions, sessions, terminal, preview HTTP, and preview WebSocket traffic.
  6. Rollback in reverse: reduce to one compatible task before disabling the flag or deploying code that cannot read v1 envelopes.

Production ECS/IaC is not present in this repository; platform settings are an explicit operations deliverable. The checked-in EC2 Compose file currently describes one backend.

Risks requiring reviewer acceptance

Broad async migration. Many services synchronously inspect local RuntimeInstance. Add descriptors first, migrate by domain, and use the full server build as the completeness gate.
At-most-once Redis delivery. Ack makes uncertainty visible and generations fence old owners, but a crash can occur around a socket write. Do not auto-retry non-idempotent commands; durable streams plus bridge deduplication are later scope.
Redis bandwidth. Preview bodies can reach 25 MiB. Bounded chunks prevent single-message spikes, but sustained preview traffic is the trigger for a dedicated gateway or private inter-replica stream.
Mixed versions. Old tasks do not understand v1 inboxes. The flag-first rollout and scale-down-before-incompatible-rollback rule are mandatory.
Approve these choices, or return the plan for revision
  • Keep WebSockets in API replicas and use Redis for presence plus directed traffic.
  • Accept reconnect—not connection migration—as the deploy guarantee.
  • Accept acknowledged at-most-once delivery in this release.
  • Use Redis chunking for endpoint traffic initially.
  • Treat multi-replica self-hosted Docker Compose support as separate unless explicitly added.
