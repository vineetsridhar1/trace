Cloud browser recording → video artifact

Add an agent-facing cloud skill and a stable trace-browser record runner. An AI can implement a change, drive a headless Chromium page with project-specific Playwright actions, save a WebM recording, and publish it through Trace's existing immutable artifact pipeline.

9–11 files 4 phases Cloud runtime image No schema or database migration

Decision

Recommended shape: keep the skill declarative and put lifecycle-sensitive behavior in one tested runtime command. The agent writes a small scenario module exporting browser actions; trace-browser owns Chromium startup, recording, teardown, output validation, and deterministic error reporting. The existing trace CLI remains the only uploader.

Scope

In scope

  • Headless Chromium tab recording inside provisioned cloud containers.
  • Agent-authored Playwright actions against localhost or a reachable URL.
  • WebM output with a bounded viewport, timeout, size check, and reliable finalization.
  • A portable skill that teaches test → record → inspect → upload.
  • Installation for both Claude and Codex in the cloud image.
  • End-to-end proof that the uploaded artifact appears as a playable video.

Not doing

  • No live browser stream or user takeover; this produces a completed artifact.
  • No audio capture in v1; Playwright's page video is the deterministic baseline.
  • No desktop/local-session support in this slice.
  • No new artifact type, GraphQL field, database table, or custom uploader.
  • No automatic recording after every code change; the agent invokes the skill when requested.

Current state

The cloud image already installs system Chromium in apps/container-bridge/Dockerfile. Existing design and animation review scripts demonstrate the repository's preferred playwright-core + system Chromium pattern, especially apps/container-bridge/animation-starter/scripts/review-animation.ts.

Agent invocations already receive an authenticated Trace CLI and skill directory through packages/shared/src/trace-invocation-env.ts. The CLI packages a file/directory and POSTs it to apps/server/src/routes/agent-artifact.ts; business validation, persistence, and the artifact_created event live in apps/server/src/services/artifact.ts.

Video is already a first-class presentation path: apps/server/src/lib/artifact-bundle.ts recognizes .webm and .mp4, the service accepts trace.video.v1, and apps/web/src/components/artifact/MediaArtifact.tsx renders a native video player. The relevant server limits are 32 MiB per uncompressed file and 64 MiB per archive/request. No backend or UI expansion is required for the first slice.

The scenario module exports one async function and receives a Playwright page; it can navigate, assert, fill, click, wait, and exercise the code under test without importing browser dependencies. The runner accepts explicit script/output/URL, viewport, and timeout flags. It launches the configured system Chromium, creates one recorded context/page, optionally navigates, runs the scenario, and always closes the page, context, and browser before resolving Playwright's video path.

On success the runner moves the finalized recording to the requested .webm path and rejects missing, empty, or over-limit output. On scenario failure it still tears down cleanly, reports the action error, and does not upload misleading evidence. The skill then directs the agent to inspect the result, keep it below the artifact ceiling, and run trace artifact push video <file> --key <descriptive-key> only after the tested flow succeeds.

Phases

Build the recording runner as an isolated unit

Add a container-bridge CLI module with strict argument parsing, scenario-module validation, fixed safe defaults (1280×720, bounded timeout), explicit Chromium lookup, deterministic temporary-directory cleanup, and post-finalization file checks. Keep the browser lifecycle injectable so unit tests can cover success and failure without starting a real browser.

Provision the media runtime in the cloud image

Add playwright-core to the container bridge's declared/install-time dependencies, install Playwright's pinned ffmpeg helper in a shared readable browser cache, retain system Chromium, and expose the compiled runner as trace-browser on PATH for the non-root coder user. Extend the Dockerfile dependency test so image drift fails fast.

Author and distribute the browser-recording skill

Add one canonical skill with a concise scenario template, readiness checks, guidance for human-readable pacing, assertion-before-upload, cleanup rules, artifact size limits, and the exact video upload command. Bake the same skill into Claude and Codex home skill directories in cloud containers, matching the repository's existing author-design-system distribution pattern. Avoid teaching direct HTTP event creation—the service-backed Trace CLI remains mandatory.

Prove the complete cloud workflow

Add a small fixture page/scenario or extend the cloud app smoke harness to record a short interaction, verify the WebM exists and stays within the upload ceiling, upload it as video, observe the resulting artifact metadata/event, and fetch the video content. Keep this smoke opt-in where it depends on a deployed cloud runtime; keep unit and image-contract tests in the regular suite.

Risks & mitigations

Playwright needs its own ffmpeg helper. System Chromium alone is not enough for recordVideo. Pin the driver in the container package, install the matching ffmpeg payload at image build time into a shared readable cache, and verify recording as the non-root runtime user.
Video finalization is asynchronous. Reading or uploading before context closure can produce a missing/corrupt file. The runner—not the skill prose—must close the context, await video.path(), then validate and move the file.
Long demos can exceed the existing 32 MiB file ceiling. Default to 1280×720 and a short bounded run, reject oversize output locally with a useful message, and teach the agent to record focused flows rather than raising server limits in v1.
Generated app readiness can be flaky. The skill should require an HTTP readiness probe and stable role/label/test-id locators before recording. The scenario must assert the final state; a video is evidence, not a replacement for test assertions.

Assumptions to approve

Product assumptions

  • V1 is cloud-only and records one headless page per artifact.
  • Silent WebM is acceptable; audio and cursor embellishment can follow later.
  • Recording is agent-invoked when requested, not an automatic post-run policy.

Technical assumptions

  • Cloud image rebuild/deploy is available for the new executable and ffmpeg payload.
  • Existing video artifact limits and native player are sufficient for focused demos.
  • The scenario module is trusted agent-authored code inside the already-isolated session container.
