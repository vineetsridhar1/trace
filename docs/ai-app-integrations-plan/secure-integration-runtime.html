Secure integration runtime for AI-generated apps

Make an AI-generated React/Node app query connected systems without ever receiving provider credentials. The first complete slice runs server-side Snowflake reads as the current viewer, a deliberately shared user, or an organization service account.

Decision and outcome

The generated Node server is the application boundary. React calls its own /api/* routes. Node code calls a server-only Trace helper. Trace owns viewer authentication, app and binding authorization, connection selection, query policy, limits, provider transport, and auditing. Nango owns provider credential storage and refresh.

Done means a CEO can connect Snowflake, authorize viewer-scoped data access, have the AI generate a fixed server-side query, publish the app, and let an employee run that same code with the employee's own Snowflake permissions. Missing connections, insufficient provider grants, unsafe SQL, forged identity, and cross-organization access all fail safely and clearly.

Scope

In scope

  • Generic Nango-backed connections and app bindings.
  • Viewer, shared-personal, and service execution identities.
  • Server-only generated-app SDK and signed viewer propagation.
  • Snowflake read queries, parameter binding, completion, limits, and errors.
  • In-app recovery when a viewer has not connected Snowflake.
  • AI authoring context, UI alignment, audit events, and E2E coverage.

Explicit non-goals

  • No helper for every provider; ordinary HTTP APIs keep one generic request path.
  • No SQL stored in Trace, manifest, or versioned operation catalog.
  • No browser-controlled SQL, role, binding, connection, warehouse, database, or schema.
  • No replacement for Snowflake grants, row policies, or masking policies.
  • No sync engine, webhook automation product, or Composio-style action catalog.

Grounded current state

The branch already contains the security foundation and a working first Snowflake request path. AppIntegrationService owns binding authorization and identity selection; EndpointProxyService authenticates the viewer and injects a short-lived context; the generated starter exposes trace.integrations.snowflake.query(); Nango stores and injects the provider credential.

Already built

Connections, signed webhooks, bindings, private app bootstrap, generic proxy, viewer token, Snowflake validator, helper, and focused security tests.

Product mismatch

The app binding UI still teaches the older browser-direct route while new generated apps should use the Node helper.

Completion gaps

The AI does not receive binding metadata automatically, an unconnected viewer gets only a raw 403, and async/partitioned Snowflake results are not normalized.

Authorization and read-only policy

Who is calling?

Private links carry no user credential. Trace authenticates the viewer, checks current organization membership and app visibility, strips forged x-trace-* headers, then injects an HS256 context scoped to user, organization, app, and endpoint for 60 seconds. The private runtime route revalidates the enabled endpoint before execution.

What may this app do, and as whom?

Trace loads the binding by the exact (bindingId, organizationId, sessionGroupId) tuple. The app owner or admin controls it. Normalized method and path allowlists constrain generic APIs. Viewer mode can resolve only the current viewer's personal connection; shared/service modes can resolve only the connection fixed on the binding.

Can this statement mutate data?

Snowflake statements are blocked from the generic proxy. The specialized route accepts one SELECT or WITH … SELECT, rejects semicolons, writes, DDL, calls, role/session changes, and SYSTEM$ operations, bounds query length, parameters, timeout, and response size, and sends values as SQL API bindings.

Provider grants remain mandatory. Static inspection cannot prove every UDF or external function is side-effect free. The Snowflake connection must use a read-only role with only required warehouse/database/schema USAGE and object SELECT.

Approval-gated implementation phases

Make bindings visible to the app-building AI

Load safe capability metadata for the current app into the existing app-session instruction assembly in apps/server/src/services/session.ts.

Only the binding contract enters the prompt; secrets and ownership internals stay out

Include binding ID, label, provider, execution identity, allowed methods/paths, and the server-helper example. Add prompt tests proving cross-app metadata and Nango identifiers never appear.

Align binding UI with the server runtime

Teach the Node helper as the default, add a Snowflake preset for POST /api/v2/statements, keep the binding ID copyable, and explain viewer/shared/service behavior plainly.

Keep generic HTTP flexibility without creating provider-specific configuration models

Reuse AppIntegrationBindingForm, AppIntegrationBindingsCard, and shadcn inputs/selects. Retain manual method/path editing for ordinary APIs; add only a convenience preset for Snowflake.

Add viewer connection recovery

Introduce stable error codes and an authenticated binding-scoped Connect bootstrap so a viewer can connect Snowflake from the app and retry.

The bootstrap reuses Nango Connect sessions but rechecks every Trace boundary

Verify viewer, organization, app, binding, and viewer execution mode before minting a provider-limited Connect session. Shared/service failures remain owner/admin problems and never prompt the viewer.

Normalize Snowflake completion

Return one typed SDK result for immediate, asynchronous, and partitioned SQL API responses within configured row, byte, and elapsed-time limits.

Poll and fetch partitions only with server-owned handles and the already-resolved connection

Never accept statement handles from the browser. Preserve the Snowflake query ID for audit correlation, map provider permission failures distinctly, and stop or cancel on timeout when supported.

Harden observability and abuse controls

Add per-viewer/per-app throttling and safe operation telemetry without recording SQL, parameters, credentials, raw provider errors, or viewer tokens.

Audit metadata is useful without becoming a data-exfiltration surface

Record app, binding, viewer actor, execution identity, provider, operation, status, duration, response bytes, and query ID. Confirm endpoint traffic capture strips the injected context and sensitive bodies.

Unify documentation and prove the two-user journey

Document one canonical React → Node → Trace → Nango → provider architecture and run the complete CEO/employee permission matrix.

Browser-direct generic proxy remains compatibility-only; Snowflake statements remain server-only

Update the starter guidance and system docs together so newly generated apps cannot be taught two conflicting paths.

Risks and mitigations

A SELECT can still invoke a side-effecting external function. Keep Trace's conservative statement validator, reject known system operations, and require a provider-side read-only role with narrowly granted objects.
Generated code is editable and can request any read allowed by the binding and provider identity. Treat the binding as a capability grant, surface it to the app owner, keep viewer permissions as the final data boundary, and audit every execution.
Async result polling can create cost or memory pressure. Use server-owned handles, hard elapsed/row/byte limits, throttling, bounded partitions, and cancellation where supported.
Assumption: Nango's configured Snowflake integration supports the SQL API and viewer-specific authorization required here. Validate this with a real two-account sandbox before production rollout; if false, only the provider adapter changes, not the Trace identity or app-auth boundaries.

Approval boundary

Approval authorizes the six phases above while preserving the existing connection and binding models. Any proposal to store SQL in Trace, expose provider credentials, broaden browser authority, or version bindings with application releases returns for separate review.
