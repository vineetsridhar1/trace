Product & architecture plan · 23 August 2026

Make the coding session a human-guided DAG.

Add Orchestrate as a first-class, repository-backed session type. One controller scopes the work with the user, proposes a ticket DAG, and coordinates ordinary coding sessions. Humans approve the plan, consequential decisions, requested recordings, and final completion.

Decision requested: approve the session boundary, durable orchestration model, human-gate policy, and one-ticket/one-commit integration contract described below.

Recommended architecture

01 · Product boundary

One Orchestrate session; many isolated coding sessions.

Recommendation

Session kind plus durable run

Add orchestrate to SessionGroupKind, then link the group one-to-one with an OrchestrationRun. The session remains the visible product object; the run holds DAG state that does not belong in session JSON.

Rejected boundary

Sibling workers in one group

Sessions inside one existing group share its branch and workdir. Parallel ticket workers there would race on the same files and make one-commit-per-ticket integration impossible to guarantee.

02 · Lifecycle

The human approves the corridor before agents move through it.

The approved plan is the autonomy boundary. Inside that corridor, the scheduler may launch ready nodes. Outside it, the service pauses the run and asks. Users may also pause the run or message any active worker at any point.

03 · Planning contract

A high-level plan sets direction; each ticket is independently executable.

04 · Durable model

Sessions carry conversations; orchestration records carry truth.

Recommended minimal models and invariants
  • OrchestrationRun is unique by sessionGroupId and stores run status, goal, concurrency, integration branch, and current head SHA.
  • OrchestrationPlanRevision stores a validated proposal and approval audit. Approval atomically materializes or updates unstarted tickets and edges.
  • OrchestrationNode links a run to a normal ticket and stores execution/review state.
  • TicketDependency is a general ticket edge. Services reject self-edges, cross-organization edges, and cycles before write.
  • TicketExecution is an immutable attempt with worker session/group, base SHA, submitted head SHA, evidence, and optional integration SHA.
  • OrchestrationDecision records the worker's choice, alternatives, consequence, and whether it is important.
  • OrchestrationGate is the source of truth for plan, question, decision, summary, recording, conflict, and final gates. Inbox items are only user-facing projections.

05 · Scheduler semantics

“Ready” means every dependency is integrated—not merely finished.

The scheduler is deterministic service logic, not an LLM polling loop. It selects nodes whose dependencies are integrated, whose gates are clear, and whose plan revision is approved. A reconciler reclaims queued/stuck work under distributed and database locks so a dropped process or duplicate event cannot launch duplicate workers.

06 · Human gates

Important decisions interrupt the run; feedback creates another attempt.

GateWhen it opensResolution
QuestionScoping or execution cannot continue without a human choice.Answer is stored with the run and the controller resumes.
PlanA new or revised DAG is ready.Approve materializes the revision; feedback creates the next revision.
DecisionA worker flags a consequential product, architecture, security, data, or scope choice.Approve the choice or return guidance for a new attempt.
SummaryThe node policy requires a human completion review.Approve or request another attempt.
RecordingThe node policy requires visible video evidence.Watch the linked video artifact, then approve or give feedback.
ConflictService-owned integration cannot apply the ticket cleanly.Choose a repair attempt, replan, or skip/cancel.
FinalEvery non-skipped node is integrated and final checks pass.Mark complete; opening/merging a PR remains an explicit action.
Recording rule

Recording is evidence, not theater. Workers use the existing browser-video skill only when its safety and browser-fit gates pass. A server-only or native ticket should use alternate proof; if the human explicitly requires video where no safe recording exists, the node stays blocked and asks.

07 · Git contract

Workers may make many commits; the final branch gets exactly one per ticket.

  • The orchestrator controller cannot commit implementation changes.
  • Each attempt records baseCommitSha and submitted headCommitSha.
  • Integration records integrationCommitSha; events never infer success from branch names.
  • Descendants become ready only after prerequisite integration commits exist.
  • Integrated history is append-only. Later feedback becomes a new ticket or compensating commit, never a history rewrite.

08 · Orchestrate workspace

The graph is the home; chat, workers, decisions, and videos are one click away.

Web ships the full graph first. Mobile can render the same normalized data as a topologically ordered, virtualized node list with “Needs you” filters before receiving a pan-and-zoom graph.

11 · Verification

Prove the state machine, the event stream, and the Git history separately.

Service and scheduler cases that must be explicit
  • Plan approval is idempotent; an older revision cannot overwrite a newer approved revision.
  • Self, cross-organization, and cyclic dependencies fail before any edge event publishes.
  • Duplicate completion reports and duplicate worker-terminated events do not create duplicate gates or attempts.
  • An execution without a valid ticket link, clean/known head SHA, or required video artifact cannot enter review.
  • Decision gates always override reviewPolicy: auto.
  • Feedback resolves the old gate and creates exactly one new attempt; the prior attempt remains queryable.
  • Concurrent scheduler replicas claim a ready node once under advisory/distributed locks.
  • Conflict leaves the integration branch unchanged and creates a visible gate.
  • Final completion is impossible with open gates, running attempts, or nonterminal required nodes.

12 · Risks, assumptions & non-goals

The largest risk is pretending a prompt is a control plane.

Assumption

One repository per run in v1

The Orchestrate group is linked to one channel repository and produces one integration branch. If multi-repo delivery is required immediately, the run/branch model and final-review experience both need another level.

Assumption

The controller is read-only

All implementation happens in ticket workers; only the integration service writes the final worktree. If the controller may edit, one-ticket/one-commit provenance becomes porous.

Open product choice

Default review policy

Recommendation: summary for user-facing tickets, auto for bounded internal tickets, and recording only when the planner can name a safe visible scenario. Important decisions block in every mode.

Open product choice

Graph interaction in v1

Recommendation: deterministic topological layout with selection, pan, zoom, and status filtering; no manual node dragging. The repository has no DAG renderer today, so avoid making layout editing part of the first release.

Explicit non-goals for the first release

  • Cross-repository ticket DAGs or a final branch spanning multiple repositories.
  • Automatically merging the final branch or pull request into its base.
  • Rewriting an integrated ticket commit after later feedback.
  • Letting agents create events directly, bypass service authorization, or infer approval from chat text.
  • Running ticket workers in the Orchestrate group's shared worktree.
  • Requiring video for work that cannot be safely and meaningfully demonstrated in a browser.
  • A full pan-and-zoom mobile graph in the first web release.
Repository facts that shaped this recommendation
  • SessionGroupKind currently includes general, coding, design, design system, app, PDF, and animation—but not orchestrate.
  • SessionGroup owns one branch/workdir shared by sessions in the group, so it is the wrong isolation boundary for parallel workers.
  • StartSessionInput.ticketId exists in GraphQL and the managed CLI, but SessionService.start does not currently consume it.
  • Tickets currently have title, description, status, priority, labels, projects, assignees, and generic links; they lack acceptance criteria and dependency edges.
  • Inbox items currently support plan and question types. Video artifacts render today, but artifact approval is intentionally limited to visual plans.
  • The entity store has no orchestration tables, and the web package has no DAG-rendering dependency.
  • AppDeploymentService already demonstrates the durable queued-state plus reconciler pattern needed for reliable scheduler claims.

Recommended decision: build Orchestrate as a first-class session group kind backed by durable run/node/execution/gate records; keep controllers read-only, workers isolated, human gates explicit, and integration service-owned. Start with scoping and sequential execution, then enable parallel scheduling after the state and Git contracts are proven.
