Review lens · deployment correctness under asynchronous failure

Can Publish be trusted when everything arrives twice?

This branch turns a temporary app-building session into a durable deployment request. Its value is not the Publish button—it is the guarantee that retries, late workers, and failed replacements cannot point a public URL at the wrong build.

The promiseOnly the newest successful checkpoint becomes the app the public URL represents.
Frozen inputEach request names an immutable Git checkpoint, never the session workspace.
One authorityPostgres deployment state decides whether a worker update still matters.
Safe replacementAn earlier live app remains live until its successor is actually live.

Four moments that must not break the promise

Read these as the product contract. The code is acceptable only if every timeline ends in the stated outcome.

A · Retry

The user presses Publish twice without changing code

Publish Acheckpoint abc
→
Publish againsame checkpoint abc
→
Reuse Aone deployment; one job

publish() holds a per-session advisory lock and returns the active deployment when it already targets that checkpoint.

B · Race

A newer checkpoint is published while the old job is still building

Publish Aabc is building
→
Publish Bdef is newer
→
A is supersededlate callback changes nothing
→
B may become liveonly via valid sequence

The old worker is allowed to finish physically; it is no longer allowed to change the product’s durable truth.

C · Bad release

A replacement fails while a previous version is already public

A is livepublic URL → abc
→
Publish Bcheckpoint def
→
B failsfailure is recorded
→
A stays liveURL never moves

A live deployment is superseded only inside the transaction that accepts a successor’s live callback.

D · Bad message

A callback is forged, repeated, or arrives out of order

Worker messagebearer token + status
→
Callback servicehash check + transition check
→
Reject or ignoreno event; no state change

Only queued → building → deploying → live (or failure) is accepted. Terminal and duplicate updates are harmless.

The key rule: a worker may do obsolete work, but it may never make obsolete work current.

Build ledger: the exact machinery behind that rule

This is the construction layer. It follows the failure story above, but identifies the concrete work and contracts needed to make each promise true.

Persist the requestschema.prisma
AppDeployment

Create a deployment row with the checkpoint and requested release shape. Store organizationId, sessionGroupId, repoId, sourceCheckpointId, commitSha, target, JSON spec, appSlug, and a hashed callback token; expose the lifecycle enum queued | building | deploying | live | failed | superseded | stopped.

Condition: a partial unique index permits only one queued/building/deploying row per session group, while the service also serializes requests with pg_advisory_xact_lock(hashtext(sessionGroupId)). Consumer: the callback service and client entity store use this row as truth. Proof: migration applies; simultaneous publishes cannot create two active rows.

Define what is deployableapp-deployment.ts
normalizeDeploymentSpec()

Normalize DeployAppSessionInput before creating the row. A static target requires a relative outputDirectory and forbids start, port, database, and migration settings. A service target requires startCommand, accepts a 1–65535 port (default 3000), a slash-prefixed healthPath, optional buildCommand, and allows migrationCommand only when database: true.

Condition: reject malformed paths, oversize commands, invalid target fields, and mismatched database/migration settings before any job exists. Consumer: the worker receives the normalized spec, not ad hoc UI input. Proof: target-specific validation tests exercise every rejected combination.

Create or reuse workAppDeploymentService.deploy()
deployAppSession

Select the latest GitCheckpoint for a managed app session, then compare both checkpoint ID and normalized spec. If an active row has both, return it without a second S3 upload or SQS message. Otherwise mark all active rows superseded, create the new queued row, emit app_deployment_queued, and dispatch it.

Condition: only a session-group manager may deploy; non-app sessions and sessions without a checkpoint fail before persistence. Consumer: GraphQL exposes deployAppSession(input); session subscribers receive the queued event. Proof: test missing checkpoint, retry with identical spec, and a new spec for the same commit.

Freeze and hand off sourceapp-deployment-dispatcher.ts
AwsAppDeploymentDispatcher.enqueue()

Archive commitSha from managed Git, not the runtime workspace. Stream git archive --format=tar.gz through a 100 MB limiter to app-deployments/{organizationId}/{deploymentId}/{commitSha}.tar.gz in S3, then enqueue a version-1 AppDeploymentJob containing IDs, commit, slug, normalized spec, source bucket/key, callback URL, and one-time token.

Condition: require AWS_REGION, TRACE_APP_DEPLOYMENT_ROLE_ARN, TRACE_APP_BUILD_SOURCE_BUCKET, and TRACE_APP_DEPLOYMENT_QUEUE_URL; any archive or enqueue failure marks this deployment failed and emits an update. Consumer: the external queue worker. Proof: stream without buffering; reject an over-limit archive; integration-test an assumed-role queue submission.

Accept only the right resultapp-deployment-callback.ts
updateFromCallback()

Expose POST /internal/app-deployments/:deploymentId/status. Require the worker’s bearer token, hash it and compare constant-time, then accept only queued → building → deploying → live or failed. Repeated callbacks and callbacks after any terminal state return the unchanged row.

Condition: a live callback must provide the stable URL https://{appSlug}.{TRACE_PUBLISHED_APP_BASE_HOST}; static deployments must provide published-apps/{appSlug}/{deploymentId}, service deployments must provide serviceName === appSlug, and image digests must match sha256:. Only then supersede the existing live row and emit app_deployment_updated. Consumer: the public routing worker and the UI. Proof: invalid credential, out-of-order status, wrong artifact prefix, wrong target artifact, and failed replacement cases.

Show durable statushandlers.ts
AppDeploymentCard

Add appDeployments to the entity store and upsert from both deployment events. Include deployment fields in SessionApplicationsState; sort that table by createdAt for a session group; render the newest row’s commit, status, failure message, and live URL in the Applications panel.

Condition: the deploy mutation is fire-and-forget—no mutation result updates Zustand. Consumer: every viewer of the session receives the same event-driven state. Proof: event-handler unit tests merge queued/updated payloads; UI test moves a displayed deployment from queued to live through emitted events.

Where the promise lives

Durable truth

AppDeployment records the checkpoint, lifecycle, callback-token hash, URL, error, and timestamps. AppDeploymentService owns authorization, locking, supersession, and monotonic transitions. Its queued/updated events feed the normal session event stream.

Visible truth

The Applications panel reads deployment entities from Zustand, not a mutation result. AppDeploymentCard shows the newest record’s checkpoint, state, failure, or live URL after the event arrives.

The intentional handoff

Trace owns the decision

Select the latest committed checkpoint; archive it from managed Git; create the durable record; enqueue a versioned job; accept only authenticated status changes.

→

The deployment worker owns execution

Build and host the archived source, then report building, deploying, live, or failed to the callback URL with its issued token.

Release gate, not a hidden implementation detail. This branch supplies Trace’s half of the handoff. Until the S3 bucket, SQS queue, assumed role, public callback URL, and a compatible queue consumer exist, publish correctly fails closed. The worker and production infrastructure are not part of this branch.
