Interactive cloud browser control and video proof

Give a cloud agent a persistent browser it can observe and control one step at a time, while it independently inspects and prepares application/database state. Recording becomes an explicit phase of that same live browser session, and the finished WebM uses Trace’s existing artifact pipeline.

Decision

Recommended architecture: the container bridge owns an invocation-scoped Playwright browser controller. The bundled trace browser CLI is a thin local client. Every inspect command returns the current URL, page title, bounded semantic snapshot, visible element references, recent console/page errors, and a screenshot path. The AI reads those observations, reasons normally, then sends one ref-based action.

This is not a pre-authored playback recipe. Browser state—page, history, cookies, storage, and authenticated session—stays alive across commands, so the agent can react to redirects, loading states, unexpected data, validation errors, and UI changes. The skill explicitly joins this browser loop with repository/API/database inspection.

Element references are grounded in the latest page, not invented CSS selectors

The controller enumerates visible actionable elements from the live page and holds the corresponding Playwright handles/locator descriptors server-side. References such as e7 are valid only for that observation generation. A re-rendered or detached element produces a stale-reference error that requires another inspect; the runner never clicks a guessed fallback element.

Observations are useful but bounded and do not expose request secrets

Semantic output prioritizes headings, labels, controls, visible text, validation state, and key attributes. It caps nodes and text length. Network diagnostics include only method, same-origin path, status, and failure reason—never headers, cookies, authorization values, or response bodies. Screenshots and observations remain local unless the agent explicitly uploads the finished video.

The state-aware workflow the skill will require

The browser controller does not mutate the database behind the application’s back. The agent uses the project’s existing state boundary, verifies the result, then observes the live UI. When UI evidence contradicts the query or source code, it loops: inspect errors, correct data/auth/route, reload, and inspect again.

Database, URL, and authentication policy

Database preparation

  1. Read schema, migrations, model/service code, existing seeds, and API routes before touching data.
  2. Prefer an existing seed/fixture/service/API because it preserves business invariants.
  3. Use parameterized, narrowly scoped SQL only when the app has no state setup seam.
  4. Query back the exact records and relationships the demo needs.
  5. Never print DATABASE_URL, credentials, tokens, or seeded passwords.

Route and session preparation

  1. Derive candidate routes from router/source code, not guesses.
  2. Probe the exact URL with curl; then let browser observations confirm redirects and rendered state.
  3. Create a demo identity through the app’s normal auth/service path.
  4. Sign in through the UI or supported auth endpoint so browser cookies/storage are real.
  5. Keep the same browser context while inspecting, changing state, reloading, and recording.
Shared/external database guardrail: the runtime default is a local Postgres database at localhost:5432/app, but an Agent Environment may inject an external DATABASE_URL. The skill must classify only the hostname (without logging the URL). For a non-loopback database it forbids reset, drop, truncate, and broad delete; demo rows must be uniquely namespaced, reversible, and removed after recording unless the user asked to keep them.
Repository evidence: app sessions already have the state primitives this workflow needs
  • apps/server/src/services/session.ts tells app agents that the managed preview is already running on port 3000 and that PostgreSQL/Redis are ready.
  • apps/container-bridge/docker-entrypoint.sh starts local Postgres and supplies a complete credentialed DATABASE_URL unless the launcher injected one.
  • docs/launcher-runtime-image-handoff.md documents the external-database override, which is why the skill cannot assume all databases are disposable.
  • apps/container-bridge/app-starter/docs/trace-apps.md identifies http://localhost:3000 as the managed app preview and requires the agent to exercise the live flow.

How recording works while the AI reasons

Continuous wall-clock capture

Starting a normal recorder before the AI reasons would produce long frozen stretches while the model reads snapshots, queries the database, and decides what to do. It also increases file size and makes failures expensive.

Action-clock capture

record start captures an opening hold. Each subsequent browser action opens a short CDP screencast segment, performs the action, captures the visible transition through settlement, and pauses the media timeline when the command returns. AI reasoning and shell/DB work between commands add no frames. record hold adds an intentional static pause; record stop finalizes and verifies WebM.

This lets the same adaptive observe–reason–act session become a concise video. There is no fragile second replay against changed data, and no need to expose credentials in a saved recipe.

Implementation phases

Define the local browser protocol and lifecycle

Add a typed request/response contract for open, inspect, navigation, ref-based actions, recording, and close. Integrate capability creation and cleanup with the container bridge’s existing invocation lifecycle.

Success criterion: two concurrent Trace sessions cannot address each other’s browser context

Tests exercise missing/wrong/revoked capabilities, invocation replacement, stale refs, one-context limits, cleanup on completion/abort, and bounded request bodies.

Implement observe–act browser control

Use playwright-core with system Chromium. Preserve a context across CLI calls; produce semantic observations and PNGs; auto-wait after actions; collect bounded same-origin diagnostics.

Observation contract: URL + title + semantic nodes + actionable refs + diagnostics + screenshot path

Action results always include the next observation. Element references carry an observation generation and fail closed when stale. Screenshots and final media live under an invocation-scoped temp directory, never in the Git worktree.

Add action-clock recording

Use Chromium’s CDP screencast frames and system ffmpeg to append only explicit action/hold segments, then verify a bounded WebM before exposing its path.

Hard limits protect runtime CPU, disk, and artifact size

Cap viewport, frame rate, per-action settlement, holds, total media duration, and encoded bytes. Stop on encoder/browser failure, delete partial output, and retain the verified file only until upload/invocation cleanup.

Expose the CLI and state-aware skill

Extend the existing bundled trace CLI with browser subcommands. Write the skill as an operational playbook spanning code/schema discovery, database classification and setup, exact URL/auth preparation, iterative inspection/action, recording, upload, and safe cleanup.

The skill must make the reasoning loop explicit, not merely list commands

It includes stop conditions: do not record until DB queries and browser observations agree; re-inspect after every navigation/action/data mutation; never act on a stale ref; never reset an external DB; never upload a video not inspected for the intended final state.

Verify the whole behavior in a built cloud image

Use a fixture app with Postgres data, authentication, redirects, loading state, and a multistep UI flow. Have the test driver prepare data, control the page adaptively, record action-clock segments, publish the video, and verify the existing Trace player.

Failure smoke: wrong DB state must be diagnosable and recoverable before recording

Start with a missing relationship so the page shows an empty/error state; inspect it; query and repair the fixture through the supported service/DB path; reload; verify the expected semantic and visual state; then record. This proves the capability requested here rather than only a happy-path click script.

Critical risks and mitigations

Database damage. A launcher can provide a shared external database even though the default is local. Classify by parsed hostname without logging secrets; prefer app-owned setup paths; forbid destructive operations externally; namespace and clean demo data.
Browser cross-talk in multi-session runtimes. Scope every context and filesystem path to a random invocation capability; never select a browser by caller-supplied session ID alone; revoke on every terminal lifecycle path.
Model acts on stale or misleading UI state. Every action is tied to the latest observation generation and returns a new observation; stale refs fail closed; the skill requires DB/source/browser evidence to agree before recording.
Secrets leak into logs or recordings. Never emit headers/cookies/DB URLs; redact fill values marked secret; avoid displaying credentials in the UI; keep inspection files local and upload only the reviewed WebM.
Runtime resource pressure. Enforce one context per invocation, global concurrency limits, bounded observations/screenshots, action-clock recording, fixed media ceilings, idle timeout, and unconditional process/temp cleanup.
