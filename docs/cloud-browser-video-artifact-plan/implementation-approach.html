Cloud browser video artifacts

Add one cloud-runtime capability: an agent can exercise its localhost app in Chromium, record a bounded browser demo, and publish that video through Trace’s already-supported artifact flow.

Decision

Recommended: ship a recipe-driven browser recorder inside the provisioned runtime image and teach agents to invoke it from a bundled browser-video skill. Keep artifact creation on the existing authenticated $TRACE_CLI artifact push video path.

This gives agents a stable, offline-capable command instead of making every session invent recording code or install browser packages. It also keeps the service layer and event model unchanged because video artifacts are already first-class.

Scope and boundaries

In scope

  • A discoverable browser-video runtime skill.
  • Fresh headless Chromium tab against a loopback URL.
  • Deterministic actions: navigate, wait, click, type, key press, pause.
  • Bounded frame capture, WebM encoding, metadata check, artifact upload.

Non-goals

  • No recording of a user’s desktop or local Chrome.
  • No audio, arbitrary remote-site crawling, persistent profiles, or downloads.
  • No local-session support in the first slice.
  • No new GraphQL mutation, event type, database model, or media UI.

Evidence: the repository already supports the complete post-recording path
  • apps/server/src/services/artifact.ts aliases video to trace.video.v1, validates video media, stores the archive, and emits artifact_created.
  • apps/server/src/lib/artifact-bundle.ts recognizes .mp4 and .webm.

Sibling pattern: reuse the existing system-Chromium launch model

apps/container-bridge/design-starter/scripts/review-design.ts already drives the system Chromium executable through playwright-core with cloud-safe flags. The new runner follows that model, while adding capture, encoding, bounded recipes, and cleanup.

Critical flow and failure behavior

The runner owns browser and encoder lifecycle. The skill owns workflow guidance and final upload. The server remains the only creator of the immutable artifact event.

Implementation phases

Package an offline-capable recorder in the cloud image

Add playwright-core and system ffmpeg, then expose a stable command backed by a typed recorder module.

Contract: JSON recipe in, verified WebM path out

The command accepts a loopback URL, viewport, output path, and finite action list. It launches the already-installed system Chromium; no per-session package or browser download is allowed.

Harden recording and cleanup

Validate input before launch; cap duration, frame rate, viewport, action count, and output size; make all failures explicit and cleanup unconditional.

Failure cases: preview unavailable, selector timeout, browser exit, encoder failure, invalid output

Use injected browser/process seams for focused tests. The command must never upload a partial result and must remove temporary frames on every exit path.

Bundle the agent skill and refresh existing runtimes

Add runtime/skills/browser-video/SKILL.md, add it to the manifest, increment the runtime version, and regenerate the embedded runtime payload.

Skill workflow: test preview → write recipe → record → inspect → artifact push

The instructions prefer short demos, visible interaction pauses, stable selectors, and $TRACE_CLI artifact push video <file> --key demo only after verification.

Prove the full handoff in a built runner image

Run a real localhost app, record multiple interactions, inspect the WebM, upload it, and verify playback in both the timeline card and artifact dialog.

Acceptance: no server/client code changes are needed for playback

The smoke test should demonstrate that the existing artifact_created event contains enough manifest data for the current Zustand event handler and media components.

Risks, assumptions, and review posture

Resource pressure. Browser capture plus encoding can consume CPU and disk. Enforce hard ceilings, use a modest default viewport/frame rate, and reject oversized output before upload.
Egress and untrusted content. First release accepts only localhost, 127.0.0.1, and ::1; recipes cannot supply Chromium flags, shell commands, downloads, or profile paths.
Automation flakiness. Require explicit selectors and waits, stop on the first failed action, and return the failing action index plus selector.
Assumption: cloud-session previews are reachable from Chromium over loopback in the same runtime container. This is true for current app/design starters. If a future adapter isolates previews in another network namespace, the runner will need an adapter-supplied preview URL rather than a recipe change.
