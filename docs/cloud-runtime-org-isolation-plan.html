Test that organizations cannot access each other’s cloud computers

We have not found evidence that this is possible today. The plan is to prove the protection with tests, then change code only if a test exposes a real hole.

3 steps Tests first No credential changes No rewrite unless a test fails

The entire plan in one sentence

Make two fake organizations, try every possible way for one to enter the other’s cloud computer, and fix only the attempts that unexpectedly work.

A simple example

Alice — Organization AHas her own session and cloud computer
→
Attempted crossoverAlice tries Organization B’s IDs and links
→
Bob — Organization BNothing opens; no information is revealed

We will repeat this with the terminal, cloud connection, app preview, files, and Git repository. Trace should reject every attempt before a command reaches Bob’s computer.

What we already know

Trace already checks

  • The signed cloud token includes the organization, user, session, and cloud-computer ID.
  • Terminal, private-preview, and Git code already checks the organization.
  • A stopped or replaced cloud computer must still match the session’s saved assignment.

AWS already blocks

  • The production cloud-computer firewall has no inbound rules.
  • The cloud computer’s AWS role has no permissions.
  • Remote ECS command access was disabled on the task we inspected.

These are good signs. The missing piece is one clear set of tests that proves all of the protections work together.

The three steps

Build the attack tests

Create Organization A and Organization B in the test environment. Try to use A’s login, tokens, IDs, and links to access B’s terminal, cloud connection, private preview, files, and Git repository.

Fix only demonstrated problems

If every attack is rejected, we do not redesign the runtime system. If one attack works, we fix that exact path so it always checks both the organization and the cloud-computer ID, then add the failing attempt as a permanent regression test.

Verify production safeguards

Add a repeatable deployment check for the AWS protections we observed: no inbound network rules, no ECS remote-command access, and no AWS permissions on the cloud-computer role.

Attacks the tests will try

Organization A tries to…Correct result
Open, list, resize, or close Organization B’s terminal.Rejected with no terminal details.
Connect as Organization B’s cloud computer.The connection closes before registration.
Send a prompt or file command using Organization B’s session or runtime ID.No command is delivered.
Open Organization B’s private app preview or preview WebSocket.Rejected before traffic reaches the cloud computer.
Use an Organization A Git token on Organization B’s repository.Rejected.
Reuse a token from a cloud computer that was stopped or replaced.Rejected.
Ask whether Organization B’s cloud computer exists.No owner, name, or other identifying information is returned.

What will not change

  • Users’ own cloud computers will continue receiving the credentials those users supplied.
  • Claude, Codex, Git, and local sessions keep working the same way.
  • We will not build a credential proxy or move credentials to a new system.
  • We will not rewrite the runtime router unless a failing test proves a change is needed.

When this is finished

The work is complete when every cross-organization attack test is rejected, normal same-organization sessions still work, the AWS checks pass, and the repository builds successfully.

Technical note for implementation

The tests will extend the existing suites beside session-router.ts, bridge-handler.ts, terminal.ts, endpoint-proxy.ts, and managed-git.ts. Any fix will stay limited to the specific path exposed by a failing test.
